# API returning HTTP 500 errors

## Symptoms

- HTTP 500 responses on customer-facing endpoints
- Elevated error rate / 5xx metric
- Application logs full of unhandled exceptions or stack traces
- Health checks failing on a downstream dependency
- Requests succeed for some traffic and fail for others (dependency-specific)

## Investigation

1. **Confirm scope** — `get_ticket` for the affected service and cluster.
2. **Check ECS health** — `get_ecs_service_health`. Compare `runningCount` to
   `desiredCount`. A shortfall means tasks are crash-looping.
3. **Correlate with deployments** — `get_ecs_deployments`. If the incident start
   time lines up with a deployment, treat that deployment as prime suspect.
4. **Read the logs** — `get_recent_logs` on the service log group, filtered to
   `ERROR`. Look for a *repeating* pattern, not one-off noise.
5. **Check the error metric** — `get_cloudwatch_metrics` for `ErrorCount5xx`
   and `LatencyP95`. Establish the shape: step change (deploy) vs gradual
   (capacity/dependency).
6. **Check CPU/memory** — `get_cloudwatch_metrics` for `CPUUtilization` and
   `MemoryUtilization`. Sustained >90% CPU can produce 500s via timeouts.
7. **Consult the matching runbook** if the logs point at a specific subsystem
   (for example `database-timeout`).

## Reading the evidence

| Observation | Likely cause |
|---|---|
| Errors began minutes after a deployment | Bad release / bad config |
| 401/403 from an internal dependency | Missing or rotated credential |
| `ConfigError`, missing env var | Configuration regression |
| Connection refused / timeout to a datastore | Dependency or network failure |
| CPU pinned near 100% | Saturation, possible hot loop |

## Possible causes

- Bad deployment (code or configuration regression)
- Missing/rotated secret or environment variable
- Database or cache connectivity failure
- Downstream dependency outage or auth failure
- Resource exhaustion (CPU, memory, file descriptors, connections)

## Possible remediation

- **Roll forward or back** to a known-good task definition (a forced new
  deployment onto a fixed definition).
- Restart the service to clear crash-looping tasks.
- Restore the missing configuration or secret, then redeploy.
- Scale out if the cause is saturation rather than a defect.

All of the above are **disruptive** and require explicit human approval.

## Verification

Do not mark the ticket resolved until **all** of these hold:

1. `get_ecs_service_health` reports `runningCount == desiredCount`.
2. The active deployment's `rolloutState` is `COMPLETED`.
3. **No ERROR log events after the remediation timestamp.**
4. `ErrorCount5xx` has returned to ~0 in the most recent buckets.
5. `LatencyP95` is back within normal range.

Use `verify_service`; it evaluates these signals for you and reports which
ones failed. Note that recent-window queries still include pre-remediation
errors — that is expected, so verification asks "any errors *since* we
remediated?" rather than "any errors in the last N minutes".
